# Architectural & Implementation Decisions — Android XR Port

This log records every meaningful architectural or implementation decision made while porting
Nightfall to Android XR (Google's Android XR platform, initial target hardware: XREAL Aura),
per the working rules in `ANDROID_XR_PORT.md`. Entries are append-only, newest last. Do not
edit past entries except to fix factual errors — add a new entry to record a change of course.

Each entry contains: date, decision, reason, alternatives considered, files/components
affected, and whether the decision is Android XR-specific or cross-platform.

---

## 2026-08-16 — Port by extending Nightfall in place, not forking

**Decision**: Add Android XR as a second supported client target inside the existing Nightfall
repository/architecture. Do not create a separate Android XR fork or rewrite the GameStream
core, video pipeline, or GDExtension.

**Reason**: Nightfall's GameStream core (pairing, session, video, audio, input) and its
low-latency Android video path (NDK `AMediaCodec` → zero-copy `AHardwareBuffer` → Vulkan import)
are the primary reasons to build on Nightfall rather than from scratch. A fork would duplicate
that work and immediately diverge, defeating the point. The audit (see
`ANDROID_XR_PORT.md`) found the large majority of the codebase — the entire GDExtension video
pipeline, the GDScript XR interaction layer, and the Android Java bootstrap — already uses
generic OpenXR/Android APIs rather than Meta-specific ones, so a fork was never structurally
necessary.

**Alternatives considered**:
- Fork the repo and rewrite the XR layer against Android XR's SDK directly. Rejected: throws
  away a working, tested low-latency video path and GameStream protocol implementation for no
  architectural gain, and would fork protocol compatibility work for Apollo/Vibepollo too.
- Rewrite the client as a flat 2D Android app using Android XR's Jetpack XR APIs instead of
  OpenXR. Rejected: loses spatial/stereoscopic rendering entirely, which is Nightfall's reason
  to exist over Moonlight Android/Artemis (see README "Why Nightfall").

**Files/components affected**: Whole-repository scoping decision; no files changed.

**Scope**: Cross-platform (governs the whole port strategy).

## 2026-08-16 — Use Godot's OpenXR-core APIs and the existing GodotOpenXRVendors plugin's Android XR support, not a custom loader

**Decision**: Rely on Godot 4.7's built-in OpenXR module plus the community GodotOpenXRVendors
plugin's Android XR vendor support (already exposed as inert export options in
`export_presets.cfg`: `xr_features/enable_androidxr_plugin`, `android_xr_features/*`) rather
than writing a custom OpenXR loader or Android XR integration layer.

**Reason**: The audit found `export_presets.cfg` (both existing Android presets) already
contains a fully-populated `android_xr_features/*` options block
(`eye_tracking`, `hand_tracking`, `tracked_controllers`, `recommended_boundary_type`,
`use_experimental_features`) alongside the active `meta_xr_features/*` block, gated by
`xr_features/enable_androidxr_plugin=false`. This is generated by Godot's Android export UI
from whichever GodotOpenXRVendors plugin version is installed locally — meaning the toolchain
already treats Android XR as a first-class vendor, the same way it treats Meta, Pico, Lynx, and
Magic Leap. Building a custom loader would duplicate functionality the toolchain already
provides and would fight upstream Godot/OpenXR tooling instead of using it (violates working
rule 3: "prefer platform abstractions... over maintaining a completely separate fork", and rule
10: "use current Android XR / Godot 4.7 / OpenXR APIs").

**Alternatives considered**:
- Hand-roll Android XR OpenXR extension bindings via GDExtension. Rejected: unnecessary — the
  vendor plugin and Godot's core OpenXR module already speak standard OpenXR, and the client's
  GDScript layer was found to be almost entirely vendor-neutral already (raycasts,
  `XRController3D`, `XRHandTracker`, `XRInterface` blend modes, core `OpenXRCompositionLayerCylinder`/
  `Quad` nodes — no `XR_FB_*`/Meta-vendor calls in any `.gd` file).
- Wait for/require a newer GodotOpenXRVendors release. Not needed yet — the export options are
  already present in this project's configuration, implying the required plugin support exists;
  it needs to be confirmed and installed locally (see "known problems" in `ANDROID_XR_PORT.md`),
  not built.

**Files/components affected**: `export_presets.cfg` (new Android XR preset to be added in
Phase 3), `addons/godotopenxrvendors/` (externally installed, gitignored — not a repo file).

**Scope**: Android XR-specific.

## 2026-08-16 — Add a new Android XR export preset instead of modifying the Quest presets

**Decision**: When Phase 3 begins, add a new `NightfallAndroidXR` preset (a `[preset.3]` block)
to `export_presets.cfg` with its own package name (e.g. `app.nightfall.androidxr`), rather than
repurposing `NightfallDev`/`NightfallRelease`.

**Reason**: Working rule 4 requires keeping existing Quest support working whenever reasonably
possible. `export_presets.cfg` already demonstrates this pattern — `NightfallDev`
(`app.nightfall.quest.debug`) and `NightfallRelease` (`app.nightfall.quest`) coexist on-device
because they use different package names (documented in `BUILD.md` "Export Presets" table). The
same technique lets a Meta-plugin Quest build and an Android-XR-plugin build install side by
side on the same physical Quest 3 (Quest still runs Android and can sideload multiple
`app.nightfall.*` packages), and keeps `build.sh` and CI-style build invocations able to target
either platform explicitly without one clobbering the other.

**Alternatives considered**:
- Add an `xr_platform` runtime flag to the existing presets and branch at runtime. Rejected for
  the export-time vendor plugin selection specifically: `enable_meta_plugin` vs
  `enable_androidxr_plugin` is an export-time Gradle/manifest decision (different AARs, different
  manifest fragments), not something that can be resolved at app runtime — Godot's Android export
  pipeline requires picking vendor plugins per export preset, not per launch.
- Replace `NightfallDev`/`NightfallRelease`'s Meta plugin with Android XR outright. Rejected:
  breaks Quest support, violates working rule 4.

**Files/components affected**: `export_presets.cfg` (future change, not yet made),
`build.sh` (will need an `--androidxr` or similar flag to stage the correct vendor AAR — the
script currently hardcodes `godotopenxr-meta-{debug,release}.aar`).

**Scope**: Android XR-specific.

## 2026-08-16 — Phase 0 audit performed without a live engine/APK build

**Decision**: Complete the Phase 0 repository audit and produce `ANDROID_XR_PORT.md` using
static code review only. Do not attempt to fake or partially fake a Godot export, GDExtension
compile, or APK build in this session.

**Reason**: The remote execution environment for this session has no Godot editor/headless
binary, no Android SDK/NDK, no `vcpkg` installation, and no connected Android/Android XR
hardware or emulator (verified: `which godot`, `ANDROID_HOME`/`ANDROID_NDK_HOME`/`VCPKG_ROOT` all
empty, no `/opt/android*`). `cmake`, `ninja`, JDK 21, and Gradle 8.14.3 are present, so C++
syntax/structure can be reasoned about, but the GDExtension cannot actually be linked (needs
`godot-cpp`, `ffmpeg`, `moonlight-common-c` etc. via vcpkg with the `arm64-android` triplet) and
no APK can be produced or installed. Per working rule 7 ("do not fake successful compilation or
testing") and rule 8 ("if something cannot be tested locally, document exactly what still needs
to be tested on-device"), the honest choice is to state this limitation plainly rather than
simulate a build result.

**Alternatives considered**:
- Attempt a partial build (e.g., compile only host-independent `.cpp` files with a bare
  `arm64-android` NDK toolchain fetched over the network) to get *some* signal. Deferred: the
  NDK, vcpkg, and Godot export templates would all need to be fetched and installed from
  scratch in this session with no guarantee of matching the pinned versions (`NDK 27.0.12077973`,
  `Godot 4.7 Beta 2`, patched engine templates) that `BUILD.md` requires for a meaningful result;
  doing so risks producing a false "it builds" signal against the wrong toolchain versions, which
  is worse than no build at all.
- Skip the audit until a properly provisioned dev machine is available. Rejected: the task
  explicitly calls for a Phase 0 static audit before any build attempt, and that audit is valuable
  and actionable on its own.

**Files/components affected**: None (process decision). See `ANDROID_XR_PORT.md` → "Build
instructions" and "Known problems" for the exact commands and tooling a developer/CI runner
needs to actually validate Phase 1.

**Scope**: Cross-platform (applies equally to verifying the existing Quest build and any future
Android XR build).
